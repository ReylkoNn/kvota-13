# Квота-13 — анализ понятности вакансий (Калининградская область, регион 39)

Прототип для хакатона «Канткод / Онлайн-отбор»: автоматически получает вакансии
с портала «Работа в России» (API региона 39) и формирует JSON-отчёт о том,
насколько понятно описаны условия работы. Отчёт помогает редактору вакансии
подготовить конкретные уточнения для работодателя.

## С чего начинается обработка

**`src/main.py`** — единая точка входа (команды `fetch` / `check` / `schedule` / `resume`).
Конфигурация: **`config.yaml`**. Ключи — только в `.env` (см. `.env.example`), в репозиторий не коммитятся.

## Быстрый старт

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt          # только pyyaml; остальное — стандартная библиотека

# Проверочный режим (без портала, без модели — правила + fallback):
python -m src.main check --input data/example_input.json --output report.json --no-ai

# Рабочий режим (скачать с API региона 39, минимум 2 страницы):
python -m src.main fetch --no-ai

# По расписанию (ежедневно в 09:00, значение из config.yaml):
python -m src.main schedule
```

## Режимы

| Режим | Команда | Что делает |
|---|---|---|
| Рабочий | `python -m src.main fetch` | Скачивает вакансии с `source_url` (пагинация `limit/offset`, по умолчанию 2 страницы, лимит `max_vacancies`), анализирует, пишет `report.json`. Повторный запуск не плодит дублей: один ID — один объект. При недоступности API код выхода 2, ошибка пишется в `report_error.json`, а **последний успешный `report.json` не перезаписывается**. |
| Проверочный | `python -m src.main check --input <json>` | Тот же анализатор на локальном JSON в формате ответов API (список или объект с `results.vacancies`/`data`/`vacancies`), без обращения к порталу. Именно этот режим использует жюри на своём наборе. |
| Расписание | `python -m src.main schedule [--cron "0 9 * * *"]` | Цикл: каждый день в заданное время сервера — `fetch`; принимается только формат `M H * * *` или `H:MM`. Альтернативы: `crontab.example`, `systemd/kvota13.{service,timer}`. GitHub workflow — демонстрационный stateless запуск без модели; он не сохраняет предыдущий отчёт между запусками. |

Настраиваются в `config.yaml`: `source_url`, `schedule_cron`, `pages`, `page_size`,
`max_vacancies`, `timeout_sec`, `output_report`, блок `ai`. Переопределение без правки
файла: `--source-url`, `--pages`, `--max-vacancies`, `--output`, `--provider`, `--model`, `--no-ai`.

## ИИ: модель, провайдер и шаг использования

**Шаг ИИ в пайплайне:** после rule-based проверки (`src/rules.py`) модель Gemma
перечитывает вакансию и ищет неоднозначные формулировки, которые правила не ловят,
и предлагает уточнения по конкретным полям. Замечания ИИ объединяются с правилами
в `src/analyzer.py` (дедупликация по теме, полю, цитате и проблеме) и **влияют на итоговый отчёт**.
В `meta.ai_status` честно указано, что сработало: `gemma-local` / `transformers-local` / `api` / `fallback` / `mixed`.

Модель получает реальные имена и значения полей источника. Замечание принимается,
только если тема допустима, поле существует и непустая цитата найдена именно в этом
поле. ИИ-заявления о противоречиях отбрасываются; пропуски и противоречия обрабатывают
правила. В журнале видно число предложенных и принятых замечаний. Статус модели означает
лишь успешный вызов, а не гарантию качества или наличия замечаний `source: ai`.
Фильтр не проверяет смысл, поэтому замечания всё равно нужно проверять редактору; возможны
и ложные срабатывания, и пропущенные моделью проблемы. Данные учебного примера синтетические.

**Модель и провайдер:**

- `local` (по умолчанию): **Gemma 2 2B IT** (`google/gemma-2-2b-it`) через **Transformers**
  на своём железе. Это gated-модель: может понадобиться бесплатный аккаунт Hugging Face, принятие лицензии и авторизация (`hf auth login`). Веса качаются при первом запуске.
  ```bash
  pip install -r requirements-ai.txt   # transformers + torch
  python -m src.main check --input data/example_input.json   # ИИ включён по умолчанию
  ```
  На CPU это может быть очень медленно. Проверяйте `ai_status`, поскольку при ошибке загрузки автоматически используется fallback.
  Модель меняется через `GEMMA_MODEL` / `--model` / `config.yaml`.
- `api`: OpenAI-совместимый API. Бесплатные варианты без покупки:
  OpenRouter (есть бесплатные модели), Groq (бесплатный tier), Google AI Studio
  (бесплатный tier, Gemini). Скопируйте `.env.example` в `.env`, укажите ключ:
  ```bash
  # .env: AI_PROVIDER=api, OPENAI_API_KEY=..., OPENAI_BASE_URL=..., OPENAI_MODEL=...
  python -m src.main check --input data/example_input.json
  ```
- `off` / `--no-ai`: только правила + fallback-лексикон (мгновенно, без зависимостей).

**Fallback:** если модель недоступна (нет `transformers`, веса не скачались, таймаут,
невалидный JSON) — срабатывает эвристический анализатор (`src/ai.py`, класс
`FallbackAnalyzer`): лексикон неоднозначностей («стабильная зарплата», «дружный
коллектив», «полный соцпакет» и т.д.) + шаблоны уточнений. Отчёт при этом не теряется,
а `ai_status` показывает `fallback`.

**Проверочный режим с моделью без аккаунта и покупки:** после установки `requirements-ai.txt`
используйте открытые веса Qwen (интернет нужен только для первой загрузки; на CPU потребуется время):

```bash
python -m src.main check --input data/example_input.json --provider local --model Qwen/Qwen2.5-0.5B-Instruct --output report.json
```

В отчёте проверьте `ai_status: transformers-local`: если указан `fallback`, модель не загрузилась
или вернула некорректный ответ; это не успешная демонстрация ИИ. Предыдущая версия протестирована
пользователем с Qwen, но новая фильтрация и Gemma на реальных моделях ещё требуют проверки.
В среде разработки доступ к Hugging Face ограничен.
Для целевой роли Gemma используйте модель по умолчанию после получения доступа. Без модели:
`--no-ai` (правила + fallback).

### Кэш и временные файлы на другом диске Windows

По умолчанию Hugging Face и pip могут сохранять данные на системном диске. Перед
запуском модели задайте в PowerShell (букву диска можно изменить):

```powershell
$base = "B:\kvota13-cache"
New-Item -ItemType Directory -Force $base, "$base\tmp" | Out-Null
$env:HF_HOME = "$base\huggingface"
$env:HF_HUB_CACHE = "$base\huggingface\hub"
$env:HUGGINGFACE_HUB_CACHE = "$base\huggingface\hub"
$env:HF_XET_CACHE = "$base\huggingface\xet"
$env:PIP_CACHE_DIR = "$base\pip"
$env:TORCH_HOME = "$base\torch"
$env:TEMP = "$base\tmp"
$env:TMP = "$base\tmp"
.\.venv311\Scripts\python.exe -c "from huggingface_hub import constants; print(constants.HF_HUB_CACHE)"
.\.venv311\Scripts\python.exe -m pip cache dir
```

Запускайте модель в том же окне, иначе переменные нужно установить снова. Эти настройки
не гарантируют отсутствия всех записей Windows и сторонних библиотек на системный диск.
Переназначение `HF_HOME` меняет и место хранения локальной авторизации Hugging Face.

## Что проверяется

Название, обязанности, требования, оплата, график, место работы, тип занятости —
по описанию **и** структурированным полям API. Если сведения есть в поле, отсутствие
их повтора в описании не считается проблемой. Отмечаются пропуски, неоднозначности
(например, «гибкий график» без дней и смен) и противоречия (оба значения в цитате).
Рекомендации подсказывают, что уточнить, без вымышленных фактов и выводов о нарушении закона.

## Формат отчёта

`report.json`: объект `{"meta": {...}, "vacancies": [...]}`. Для каждой входной вакансии —
отдельный объект с `id`, `url` (ссылка на карточку из источника, иначе `null`), `title`, `ai_status` и массивом `remarks`
(если замечаний нет — пустой массив). `meta` содержит `generated_at`, `mode`
(`fetch`/`check`), `source`, `ai_status`, счётчики.

Каждое замечание: `topic` (тема), `field` (поле источника), `quote` (цитата/значение;
для пропуска — пустая строка; для противоречия — оба значения через ` | `),
`problem` (суть проблемы), `recommendation` (конкретная рекомендация),
`severity` (`высокая`/`средняя`/`низкая`), `source` (`rule`/`ai`/`fallback`).

Пример: `data/example_report.json` (сгенерирован из `data/example_input.json`).

### Сценарий видео (до 3 минут)

Запись и публичная ссылка ещё не подготовлены; перед сдачей их нужно добавить в README.
1. Покажите настройку источника, лимита и расписания в `config.yaml`; запустите `fetch`.
2. Покажите `src/ai.py`, затем `check` с доступной моделью и её `ai_status`.
3. Откройте JSON и покажите ID, цитаты и рекомендации, а также fallback при отсутствии модели.
4. По желанию покажите `resume` с вымышленными данными. Проверьте доступность ссылки без авторизации.

Рабочий API из текущей среды проверить не удалось: исходящие соединения к порталу ограничены.
Перед сдачей запустите `fetch` в сети с доступом к порталу и проверьте актуальный формат ответа.

Для постоянного расписания скопируйте unit-файлы из `systemd/` в systemd, исправьте
`WorkingDirectory` и `ExecStart` (укажите Python из виртуального окружения), выполните
`systemctl daemon-reload` и `systemctl enable --now kvota13.timer`. Таймер использует
локальное время сервера; отчёт хранится в рабочем каталоге и не заменяется при ошибке API.

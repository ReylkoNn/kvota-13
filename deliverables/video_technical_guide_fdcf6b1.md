# Инструкция для записи видео: vacancy-check

**Проверенная версия:** `aufBruderschaft/vacancy-check`, коммит `fdcf6b129b8d626aad581186757795626ac90e4e`. Исходный код: https://github.com/aufBruderschaft/vacancy-check/tree/fdcf6b129b8d626aad581186757795626ac90e4e

Если команда после этой версии внесёт изменения, перепроверьте команды, примеры и укажите новый итоговый SHA. Ниже — техническая памятка для подготовки и записи, а не утверждение, что все требования уже выполнены.

## 1. Что показывает проект

Программа получает вакансии из локального JSON или API «Работа России», нормализует поля и объединяет записи с одинаковым ID. Правила ищут пропуски, неясности и некоторые противоречия. При включённом ИИ каждая вакансия дополнительно отправляется локальному OpenAI-совместимому сервису Ollama. В стандартной конфигурации используется `gemma4:e2b`.

Модель предлагает замечания; приложение проверяет поля и цитаты, отклоняет неподтверждённые замечания, убирает некоторые дубли правил и формирует JSON. Проверка цитат сама по себе не гарантирует правильность вывода: смысл проверяется вручную.

Доступные режимы: `check` — локальный файл; `run` — API; `schedule` — первый запуск сразу, далее по интервалу. Это CLI-приложение, а не готовый веб-интерфейс.

## 2. Что уже проверено независимо

- В отдельном чистом окружении установлены зависимости проекта; **22 автоматических теста прошли**. Тесты ИИ используют имитацию сервиса и не доказывают качество реальной модели.
- Команда проверки учебного файла с `--no-ai` отработала: 10 вакансий и 7 замечаний правил.
- В репозитории есть пример `data/example_report.json`: 10 вакансий, модель указана как `gemma4:e2b`, 7 замечаний с `source: llm` и 6 с `source: rules`. Это **опубликованный командой пример**, а не независимо запущенная нами модель. Проверять фактические замечания по смыслу перед показом.
- Сам `gemma4:e2b`, Ollama и боевой API в данной среде независимо не запускались. Полное соответствие ТЗ и скрытый набор не проверены.

## 3. Подготовка Windows до записи

### 3.1. Исходники

Взять именно указанный коммит: [страница коммита](https://github.com/aufBruderschaft/vacancy-check/commit/fdcf6b129b8d626aad581186757795626ac90e4e), [ZIP этого снимка](https://github.com/aufBruderschaft/vacancy-check/archive/fdcf6b129b8d626aad581186757795626ac90e4e.zip). Распаковать в отдельную папку и открыть PowerShell именно в папке, где лежат `main.py` и `config.yaml`. Не копировать старые `app/llm.py`, сторонние эксперименты или конфиги из прежних версий проекта.

Проще всего в Проводнике открыть эту папку, щёлкнуть по адресной строке, написать `powershell` и нажать Enter. Проверить:

```powershell
Test-Path .\main.py
Test-Path .\config.yaml
```

Обе команды должны вывести `True`. Не включать в репозиторий `.venv`, модели, `reports/cache.json`, токены и реальные чувствительные данные.

### 3.2. Python

Python 3.11 рекомендуется; в PowerShell из корня нового проекта:

```powershell
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -q
```

Если команда `py` не найдена, сначала установить Python 3.11 с официального сайта или использовать известный путь к установленному Python. Активация виртуального окружения не нужна. Зависимости Ollama и модели этой командой не устанавливаются. Установка Python-зависимостей требует сети или заранее подготовленных пакетов.

Ожидаемый итог тестов на этом коммите: `Ran 22 tests ... OK`. Тесты могут печатать предупреждения, так как имитируют ошибки. Проверяйте именно итог.

### 3.3. Ollama и диск B:

Проект использует **Ollama**, а не ранее настроенное окружение Transformers. Старый кэш Hugging Face не является кэшем Ollama; наличие `google/gemma-2-2b-it` не означает, что `gemma4:e2b` уже скачана. Команды ниже не требуют платного аккаунта, но установка и первая загрузка требуют интернета и достаточно свободного места. Веса и работоспособность модели нужно проверить заранее на компьютере для записи.

1. Установить Ollama для Windows с официальной страницы https://ollama.com/download/windows. Программа Ollama и её журналы по умолчанию могут занимать место на системном диске, даже если веса помещены на B:. См. https://docs.ollama.com/windows.
2. **До загрузки модели** настроить пользовательскую переменную `OLLAMA_MODELS` на папку, например `B:\kvota13-cache\ollama-models`. На Windows: «Изменение переменных среды вашей учётной записи» → пользовательские переменные → создать `OLLAMA_MODELS` с этим путём. Если Ollama уже работает, полностью выйти из неё через значок в трее и запустить заново: сервер должен унаследовать новую переменную. Одного `$env:OLLAMA_MODELS=...` в окне клиента недостаточно, если сервер уже работает с другим окружением.
3. При изменении расположения **уже скачанные веса автоматически не перемещаются**; не удаляйте старые папки и не скачивайте лишнюю копию, пока не проверили, где у команды лежит модель. В самой программе сохранение отчёта и кэша ответов остаётся в папке проекта `reports/`.
4. В новом PowerShell проверить службу и наличие модели:

```powershell
ollama --version
ollama list
```

Если службы нет, запустить приложение Ollama. Не запускать второй `ollama serve`, если служба уже работает. Если модели в списке нет и настройка диска подтверждена:

```powershell
ollama pull gemma4:e2b
ollama list
```

Скачивание может быть большим: на странице https://ollama.com/library/gemma4 указан диапазон размеров `e2b` 4,6–7,5 ГБ в зависимости от варианта. Оставьте запас на диске и в оперативной памяти. Для GTX 1660 с 6 ГБ VRAM не обещаем, что модель поместится целиком в GPU: часть может выполняться на CPU, а обработка — быть медленной. Проверьте заранее. Версия Ollama и совместимость structured output тоже должны быть проверены реальным запуском.

В `config.yaml` проекта по умолчанию указаны `llm.enabled: true`, `base_url: http://localhost:11434/v1`, `model: gemma4:e2b`. Это **локальный Ollama на том же компьютере**, не публичная веб-служба. Не указывайте внешний адрес без согласия на передачу вакансий.

## 4. Подготовить отчёты ДО записи

### 4.1. Проверка правил, без ИИ

```powershell
.\.venv\Scripts\python.exe main.py check --input data/kantkod_sample_vacancies.json --no-ai
```

Открыть `reports/report.json` в редакторе. Здесь `model: null`, `llm_checked: false`, `llm_status: disabled`; это **не демонстрация ИИ**. Эти данные позволяют увидеть вклад правил.

Сохраните копию отдельно, чтобы следующий запуск не перезаписал её:

```powershell
Copy-Item .\reports\report.json .\reports\report-no-ai.json
```

### 4.2. Прогон полного учебного файла с ИИ

Убедитесь, что Ollama запущена, модель скачана и в `config.yaml` включён ИИ:

```powershell
.\.venv\Scripts\python.exe main.py check --input data/kantkod_sample_vacancies.json
```

Дождаться завершения. В зависимости от компьютера это может занять заметное время. Последний отчёт: `reports/report.json`. Его можно открыть без изменения содержимого:

```powershell
Invoke-Item .\reports\report.json
```

В отчёте проверить:
- `model` — имя модели, но **само по себе не доказывает** наличие полезных замечаний;
- `source: llm` — проверенное приложением замечание модели; сопоставить его с исходной вакансией и проверить смысл;
- `source: rules` — замечание правила, не ИИ;
- `llm_status: model` — ответ модели в текущем запуске; `cache` — ранее сохранённый результат; `error`, `disabled`, `skipped_limit` — не успешная проверка модели в этом запуске;
- `llm_checked: true` может соответствовать и пустому списку, а в этом коммите — также случаю, когда все замечания отклонены и преобразованы в пустой результат. Не говорить, что каждый `true` означает полезный вклад ИИ.

Если модель недоступна, программа может всё равно сохранить отчёт правил. Это не успешная демонстрация ИИ; проверьте логи и `source`, а не только сообщение об успешном сохранении. Повторные запуски могут читать `reports/cache.json`: для честного показа обязательно различать `cache` и реальный свежий вызов модели.

Удобный подсчёт без изменения отчёта (одна строка):

```powershell
.\.venv\Scripts\python.exe -c "import json,collections; r=json.load(open('reports/report.json',encoding='utf-8')); print('model:',r['model']); print('vacancies:',len(r['vacancies'])); print('statuses:',dict(collections.Counter(v.get('llm_status') for v in r['vacancies']))); print('sources:',dict(collections.Counter(i.get('source') for v in r['vacancies'] for i in v['issues'])))"
```

Для показательного сравнения найдите **одну и ту же вакансию** в `report-no-ai.json` и `report.json`; убедитесь, что в отчёте с ИИ появилось обоснованное `source: llm`, которого нет в варианте без ИИ. Проверьте цитату в `data/kantkod_sample_vacancies.json`. Если такого различия в своём прогоне нет — не утверждайте, что модель повлияла на отчёт: сначала устраните причину.

Дополнительная формальная проверка 10 учебных вакансий, **без кэша**:

```powershell
.\.venv\Scripts\python.exe -m tools.verify_model --output reports/model-verification.json
$LASTEXITCODE
```

`0` — заложенные в инструмент формальные ожидания совпали; `1` — есть несовпадения; `2` — ошибка или модель недоступна. Это не гарантия корректности смысла или полноты. У этого коммита есть ограничение: при полном отклонении замечаний модели инструмент может трактовать результат как пустой, поэтому для «чистых» примеров такой результат способен выглядеть успешным. Проверять логи и содержание вручную.

### 4.3. Живой показ на одной вакансии, если полный прогон слишком долгий

Чтобы записать короткий реальный вызов, сначала создать файл с одной учебной вакансией; эти команды не содержат русских строк PowerShell и не перезаписывают исходный файл:

```powershell
.\.venv\Scripts\python.exe -c "import json; from pathlib import Path; from app.fetch import load_local; v=[x for x in load_local('data/kantkod_sample_vacancies.json') if x.get('id')=='DEMO-39-002']; assert len(v)==1; Path('one-vacancy.json').write_text(json.dumps(v,ensure_ascii=False,indent=2),encoding='utf-8')"
```

Для свежего вызова не удаляйте кэш без необходимости: в отдельной временной копии проекта либо после сохранения прежнего файла можно временно переименовать `reports/cache.json`. При записи честно показывайте, что это одна вакансия, а не весь набор. Затем:

```powershell
.\.venv\Scripts\python.exe main.py check --input one-vacancy.json
```

**Внимание:** эта команда перезапишет `reports/report.json` отчётом на одну вакансию. Сначала сохраните копию полного отчёта. Если в результате нет подходящего `source: llm`, не изображайте успешный результат — покажите подготовленный пример отдельно и подпишите его как пример из репозитория.

## 5. API и расписание

В `config.yaml` задаются адрес API `source.url`, `page_size`, `max_vacancies`, число повторов и задержка; `schedule.every_hours` — период. API-лимит не ограничивает локальный `check`. В этой версии скрипт может уменьшить размер страницы, чтобы при достаточном количестве данных запросить не менее двух страниц. Повтор ID объединяется; запись без корректного ID вызывает ошибку.

```powershell
.\.venv\Scripts\python.exe main.py run
.\.venv\Scripts\python.exe main.py schedule
```

`run` делает запрос к внешнему API. `schedule` стартует сразу и затем ждёт заданное число часов; окно/процесс должен оставаться запущенным, остановка — `Ctrl+C`. При неудачном плановом запуске следующая попытка через меньший из интервала и часа. Для автоматической работы при выключенном окне нужен системный планировщик или служба — в самом проекте это не настроено. Для демонстрации без ИИ к каждой из этих команд можно добавить `--no-ai`, но это будет только демонстрация правил.

Команды при проблеме загрузки API стремятся сохранить последний отчёт, а запись отчёта делается через временный файл. Однако оговорку о неполных ответах API см. в разделе 7: нельзя обещать защиту от любых ошибок или доказанную обработку всех страниц.

## 6. Сценарий видео до 3 минут

Не нужно ждать загрузку модели или весь прогон на записи: подготовьте их заранее, а длинные участки честно сократите монтажом. Показать реальный статус и происхождение результата, не выдавать пример или кэш за новый запуск.

| Время | Экран | Что сказать |
|---|---|---|
| 0:00–0:20 | Публичный репозиторий и итоговый SHA | «Проверяем вакансии на пропуски, неясности и противоречия. Исходники и пример отчёта доступны публично». |
| 0:20–0:45 | `config.yaml`: источник, лимит, расписание, модель | «Параметры API, число вакансий и период задаются в YAML. ИИ работает через локальный Ollama». |
| 0:45–1:15 | Терминал: `check --input ...` и его фактический результат; при долгом ожидании сокращённый монтаж | «Запускаем локальный учебный файл. Полный прогон обрабатывает все переданные вакансии с корректными ID; дубли ID объединяются». Если показываете одну запись — так и сказать. |
| 1:15–2:10 | Сравнение одного ID в двух отчётах: без ИИ и с `source: llm`; исходный текст | «Правило отмечает пропуск, а модель добавила замечание по содержанию». Показать фактическую цитату и рекомендацию; убедиться, что это действительно новые данные, а не только кэш или заготовка. |
| 2:10–2:35 | `run`, `schedule` и выходной путь в конфиге | «Режимы позволяют запускать проверку вручную, из API и с интервалом, пока процесс работает». Не утверждать, что веб-сервис уже развёрнут. |
| 2:35–2:55 | Итоговый отчёт и ссылка на репозиторий | «Результат — JSON; модель может ошибаться, поэтому сомнительные выводы нужно проверять». Указать ссылку на опубликованное видео и участников в итоговой документации. |

Пример в репозитории по `DEMO-39-002` содержит замечание ИИ о расплывчатых поручениях, а правила указывают отсутствие зарплаты. Сначала проверьте, что **в вашем реальном прогоне** это тоже так. Для `DEMO-39-004` фактическое явное противоречие — удалёнка в `duty` и ежедневный офис в `requirement.qualification`; опубликованный пример ссылается на адрес вместо обязательного присутствия, поэтому его не стоит безоговорочно показывать как безупречное доказательство противоречия.

## 7. Важные замечания команде до сдачи

1. **Отклонённые ответы маскируются под пустой успех.** В `main.py` при `LLMAllRejected` текущий код присваивает `llm_issues = []`, затем помечает `llm_checked: true`, `llm_status: model` и сохраняет `[]` в кэш. Проверено воспроизведением с имитацией. Логически это не то же самое, что корректный ответ модели `[]`; рекомендуется не кэшировать такой случай как успех и дать отдельный статус. Это может влиять и на `tools.verify_model`.
2. **Не всякая ошибка API отличима от пустой страницы.** `unwrap({'results': {'error': '...'}})` возвращает `[]`; если такой объект пришёл после нормальной страницы, текущий код может принять его за конец данных и сохранить частичный отчёт. `results: {}` явно считается концом по решению автора; ошибки внутри `results` стоит проверять отдельно. Воспроизведено с имитацией, реальную форму ошибки API не утверждаем.
3. `README.md` в проверенном коммите содержит только заголовок. Нужны проверенная инструкция запуска, ссылка и SHA, конфигурация расписания, вклад участников, пример отчёта и ссылка на публичное видео. Видео до 3 минут ещё нужно записать и опубликовать.
4. В примере `DEMO-39-004` модель трактует адрес как доказательство офиса; сам адрес не доказывает обязательное присутствие. Лучше опираться на текст требования об обязательном ежедневном офисе. В `008` фиксированный и гибкий график могут требовать уточнения, но не обязательно являются прямым противоречием; экспертная проверка важна.
5. В тексте на скриншоте утверждение «Transformers/Hugging Face всегда требует аккаунт» слишком широкое: открытые модели могут быть доступны без аккаунта; у конкретной gated-модели Gemma могут потребоваться доступ/авторизация. Выбор Ollama в этой версии обоснован возможностью локального запуска, но сам факт его выбора не заменяет проверку реальной модели и условий её использования.
